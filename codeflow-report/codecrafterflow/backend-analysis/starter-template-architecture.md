# Starter Template Architecture — Deep Analysis

## Repository Structure (Python/Shell Challenge)

```
codecrafters-shell-python/
├── app/
│   └── main.py              ← USER'S CODE LIVES HERE (entry point)
├── .codecrafters/
│   ├── compile.sh            ← Build step (empty for Python, used for compiled langs)
│   └── run.sh                ← Execution wrapper — how CodeCrafters runs user code
├── codecrafters.yml          ← Challenge configuration (language version, debug mode)
├── your_program.sh           ← LOCAL execution wrapper (does NOT affect remote grading)
├── pyproject.toml            ← Python project metadata (uv-based)
├── uv.lock                  ← Dependency lock file
├── .python-version           ← Python version pinning
├── .gitattributes            ← `* text=auto` — normalize line endings
├── .gitignore
└── README.md                ← Progress badge + instructions
```

## Critical Architecture Insights

### 1. The `.codecrafters/` Directory — The Execution Contract
This is the **interface contract** between the user's code and the grading system.
- **`compile.sh`**: Called FIRST by the grading pipeline. For compiled languages (Rust, Go, C, etc.), this handles compilation. For Python, it's a no-op.
- **`run.sh`**: Called SECOND. This is how the grading sandbox actually executes the user's code.
  - Uses `uv run` (modern Python package manager) with `PYTHONSAFEPATH=1` to prevent import hijacking.
  - Runs `app.main` as a module (`-m app.main`).
  - Passes `"$@"` — meaning the grading harness can pass arguments to the user's program.
- **Design Philosophy**: The `.codecrafters/` scripts are the "serverless function handler" — they abstract the language runtime so the grading pipeline doesn't need to know how to compile/run every language. It just calls `compile.sh` → `run.sh`.

### 2. `codecrafters.yml` — User-Facing Configuration
```yaml
debug: false          # Toggle verbose logging during grading
buildpack: python-3.14  # Runtime version selection
```
- **`debug`**: When `true`, the grading pipeline emits detailed logs. This is how CodeCrafters provides transparency without exposing internal test logic.
- **`buildpack`**: Maps to a **Docker image tag** on the backend. Each buildpack is a pre-built container image with the specified runtime installed. This is how they support 20+ languages efficiently.

### 3. `your_program.sh` vs `.codecrafters/run.sh`
- `your_program.sh`: Copied from `run.sh` but for **local testing only**. Changes to this file are explicitly documented as NOT affecting remote grading.
- `.codecrafters/run.sh`: The **canonical execution script** used by the grading pipeline.
- **Why separate?** Users can customize their local workflow (e.g., add breakpoints, environment variables) without breaking the grading contract.

### 4. `README.md` — Dynamic Progress Badge
```markdown
[![progress-banner](https://backend.codecrafters.io/progress/shell/d1fe6aab-9b89-461e-8e5a-413b3205d78b)](...)
```
- The badge URL contains a **UUID** (`d1fe6aab-9b89-461e-8e5a-413b3205d78b`) — this is the **repository/attempt ID**.
- The badge image is dynamically generated by `backend.codecrafters.io`, meaning it updates in real-time as the user progresses.
- **Backend implications**: The backend has a `/progress/:challenge/:attempt_id` endpoint that renders a dynamic SVG/PNG badge showing completion percentage.

### 5. Git Configuration
- **Remote**: `https://git.codecrafters.io/23e6d7439485685e` — UUID-based repo slug on their custom Git server.
- **Branch**: `master` (not `main`) — this is significant; the grading pipeline likely listens for pushes to `master`.
- **Initial Commit**: `init [skip ci]` — The `[skip ci]` tag suggests their Git server has a CI/CD-like trigger that can be skipped.
- **Authentication**: Standard HTTPS with username:PAT as credentials embedded in the remote URL.

### 6. The `app/main.py` Starter Template
```python
import sys

def main():
    # TODO: Uncomment the code below to pass the first stage
    # sys.stdout.write("$ ")
    pass

if __name__ == "__main__":
    main()
```
- **Pedagogical Design**: The solution is literally commented out in the starter code. Stage 1 is designed to be a **zero-friction win** — just uncomment one line.
- **Psychology**: This guarantees the user's first interaction is a success, building confidence and momentum.
- **Progressive Scaffolding**: Later stages require the user to write new code, but the first stage uses "uncomment to win" to reduce the cognitive barrier to entry.

## Admin Perspective — How Templates Are Created

The admin/challenge-creator likely:
1. Creates a **template repository** for each (challenge, language) pair.
2. Defines the `.codecrafters/compile.sh` and `.codecrafters/run.sh` scripts specific to that language's toolchain.
3. Writes the initial `app/main.py` (or equivalent) with TODO comments guiding Stage 1.
4. Configures `codecrafters.yml` with available `buildpack` options.
5. When a user starts a challenge, the backend **forks** this template into a unique user-specific repo (UUID-based).
